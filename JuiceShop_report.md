# Звіт з лабораторної роботи: OWASP Juice Shop — перші кроки у веб-безпеці

**Виконав:** студент
**Стенд:** OWASP Juice Shop (навмисно вразливий застосунок на Node.js, Express, Angular)
**Інструменти:** браузер, Docker, DevTools, gobuster, техніка обходу фільтрів файлів

## Мета роботи

OWASP Juice Shop — один із найпопулярніших навчальних стендів для практики веб-безпеки: понад сотня челенджів різного рівня складності в одному застосунку. Мета цієї роботи — пройти перші, «вступні» етапи: підняти застосунок локально, знайти приховану панель зі списком завдань, виконати базову XSS-атаку, знайти конфіденційний файл через некоректну конфігурацію сервера і, нарешті, обійти форму логіна за допомогою SQL-ін'єкції.

## Хід виконання

### Крок 1. Розгортання застосунку

Найшвидший спосіб підняти Juice Shop локально — контейнер Docker, оскільки він одразу дає ізольоване й повністю відтворюване середовище:

```
docker run --rm -p 3000:3000 bkimminich/juice-shop
```

Після старту контейнера відкрив у браузері `http://localhost:3000` і побачив головну сторінку магазину з переліком «соків»:

### Крок 3. DOM-based XSS через поле пошуку

Наступна задача — виконати класичну DOM XSS-атаку. Поле пошуку вгорі сторінки не фільтрує вхідні дані належним чином, тож вставив туди корисне навантаження:

```html
<iframe src="javascript:alert('xss')">
```

Застосунок одразу зарахував челендж «DOM XSS» — саме сам факт вставки такого рядка в пошук уже призводить до виконання скрипта в контексті сторінки:

<img width="1935" height="1268" alt="14" src="https://github.com/user-attachments/assets/0fc4002f-0e4d-4f56-ab2a-61ffc53df5b9" />


Після основного завдання є ще й «бонусний» варіант — той самий принцип, але з реальним корисним навантаженням (вбудований плеєр SoundCloud замість простого `alert`). Підставив довший iframe із посиланням на трек, і система зарахувала другий, «бонусний» челендж поверх основного:

```html
<iframe width="100%" height="166" scrolling="no" frameborder="no" allow="autoplay" src="https://w.soundcloud.com/player/?url=https%3A//api.soundcloud.com/tracks/771984076&color=%23ff5500&auto_play=true&hide_related=false&show_comments=true&show_user=true&show_reposts=false&show_teaser=true"></iframe>
```

### Крок 4. Витік конфіденційних даних через неправильну конфігурацію сервера

Тут задача складніша — потрібно знайти файл, який узагалі не мав бути публічно доступним. Спочатку спробував просканувати приховані директорії інструментом на кшталт gobuster, але перший запуск завершився помилкою через неправильні параметри сканування; після виправлення налаштувань (правильний список слів і розширення файлів) сканування вже дало результат і показало наявність директорії `/ftp`.

Під час одного з тестових запитів застосунок несподівано «впав» із детальним повідомленням про помилку — цим самим я побічно пройшов ще один челендж, «Error Handling» (Security Misconfiguration), оскільки такий рівень деталізації помилки в проді видавати не повинен. Перезапустивши контейнер, перейшов безпосередньо до знайденої FTP-директорії за адресою `http://localhost:3000/ftp` — там дійсно лежали резервні копії та `.md`-файли:

Сервер, однак, блокує пряме завантаження деяких із цих файлів. Обійшов це обмеження технікою **Poison Null Byte** — додав до назви файлу закодований нуль-байт (`%2500`) перед розширенням `.md`, і сервер, замість того щоб відмовити в доступі, віддав повний вміст файлу:

<img width="1938" height="1306" alt="16" src="https://github.com/user-attachments/assets/679000ba-be07-45ca-99f3-6b35d1a8eef9" />


Той самий трюк спрацював і для решти файлів у директорії. У підсумку лише завдяки цій одній техніці одразу зарахувалось кілька челенджів — «Forgotten Developer Backup», «Poison Null Byte» та «Misplaced Signature File»:

### Крок 5. Обхід автентифікації адміністратора через SQL-ін'єкцію

Останній крок цього базового проходження — класична SQLi-атака на форму логіна, яка дозволяє увійти в систему, взагалі не знаючи пароля. У полі email ввів:

```
' or 1=1--
```

а в полі пароля — будь-яке довільне значення (сервер туди навіть не заглядає, оскільки запит обривається раніше):

<img width="1944" height="1320" alt="23" src="https://github.com/user-attachments/assets/27475efe-e09b-4fbe-973a-f6efb050c6e5" />


**Чому це працює.** Запит до бази даних на бекенді, найімовірніше, побудований конкатенацією рядків і виглядає приблизно так:

```sql
SELECT * FROM Users WHERE email = '' OR 1=1--' AND password = '...'
```

Умова `1=1` завжди істинна, а `--` перетворює все, що йде після неї (включно з перевіркою пароля), на коментар. У результаті запит фактично повертає першого користувача з таблиці — в базі Juice Shop це саме адміністратор, тож вхід відбувається одразу під адмінським акаунтом. Це підтвердив і сам застосунок, зарахувавши челендж «Login Admin», після чого в кошику вже видно активну сесію під новим акаунтом:

## Інструменти, які знадобилися

| Інструмент | Навіщо використовував |
| :--- | :--- |
| **Docker** | Швидкий і відтворюваний запуск застосунку локально. |
| **DevTools браузера** | Пошук прихованих маршрутів у скомпільованому JS-коді (`main.js`). |
| **gobuster** | Автоматизований перебір прихованих директорій і файлів на сервері. |
| **Технологія Poison Null Byte** | Обхід перевірки розширення файлу на стороні сервера. |

## Висновок

За час цієї практики я пройшов шлях від простого запуску контейнера до кількох незалежних класів атак: DOM XSS через недостатню фільтрацію пошукового поля, розкриття конфіденційних файлів через неправильну конфігурацію веб-сервера (плюс обхід блокування через Poison Null Byte), і, нарешті, повний обхід автентифікації через класичну SQL-ін'єкцію в формі логіна. Показово, що більшість цих проблем не пов'язані між собою напряму, але мають спільний корінь — застосунок або взагалі не перевіряє вхідні дані користувача (пошук, форма логіна), або неправильно налаштований на рівні інфраструктури (відкрита FTP-директорія, надто детальні повідомлення про помилки). Це добре демонструє, що безпека застосунку — це не одна вразливість, яку можна «залатати», а сукупність практик: валідація вводу, параметризовані запити, коректна конфігурація сервера і продумана обробка помилок.
