## Мета роботи

Розібратися, що таке SQL і як він влаштований зсередини (DML, DDL, DCL), а потім на практиці показати, як відсутність фільтрації вхідних даних дозволяє «підмінити» логіку SQL-запиту — від найпростішого читання чужих даних до зміни зарплати і видалення таблиць. Окремо — показати, як SQL-ін'єкція здатна порушити всі три складові тріади CIA: конфіденційність, цілісність і доступність.

## Теоретична частина

### Що таке SQL

SQL (Structured Query Language) — стандартизована мова (стандарт ANSI закріплений у 1986 році, ISO — у 1987-му) для роботи з реляційними базами даних. Дані в такій базі організовані у вигляді таблиць: рядки — це окремі записи, стовпці — окремі поля запису, а індекси прискорюють пошук потрібних рядків.

Для практики в уроці використовується таблиця `employees` з полями `userid`, `first_name`, `last_name`, `department`, `salary` та `auth_tan` (номер для автентифікації транзакцій).

Команди SQL прийнято ділити на три групи:

1. **DML (Data Manipulation Language)** — робота із самими даними: `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
2. **DDL (Data Definition Language)** — робота зі структурою бази: `CREATE`, `ALTER`, `DROP`.
3. **DCL (Data Control Language)** — керування правами доступу: `GRANT`, `REVOKE`.

Кожна з цих груп цікава для атакуючого по-своєму: DML дає доступ до самих даних, DDL дозволяє змінювати чи знищувати структуру бази, а DCL — маніпулювати правами користувачів аж до отримання адмінських привілеїв.

### Що таке SQL-ін'єкція

SQL-ін'єкція — це вбудовування довільного SQL-коду через звичайне поле вводу застосунку. Якщо бекенд формує запит простою конкатенацією рядків (наприклад, `"SELECT * FROM users WHERE name = '" + userName + "'"`) і не використовує підготовлені вирази (prepared statements), то будь-який спецсимвол на кшталт лапки `'`, крапки з комою `;` чи коментаря `--`, який користувач впише у форму, може змінити сенс запиту.

Наскільки серйозними будуть наслідки — залежить не лише від самої вразливості, а й від:

- прав облікового запису, під яким застосунок ходить у базу (принцип найменших привілеїв тут дуже допомагає обмежити збитки);
- наявності додаткових рівнів захисту (WAF, валідація вводу);
- конкретної СУБД — наприклад, MS SQL Server має розширені процедури на кшталт `xp_cmdshell`, які дозволяють виконувати команди прямо в ОС сервера, тож ін'єкція там потенційно набагато небезпечніша, ніж у більш «замкнутих» базах.

## Хід виконання

### Крок 1. Знайомство з таблицею та звичайний SELECT

Спершу переглянув приклад таблиці `employees` і виконав найпростіше завдання — дізнатися відділ співробітника Bob Franco звичайним запитом на читання, без жодних трюків:

```sql
SELECT department FROM employees WHERE first_name = 'Bob' AND last_name = 'Franco';
```

![Урок SQL Injection (intro): теорія та перше завдання на SELECT](screenshots/sql-intro-practice.png)

### Крок 2. DML — зміна чужих даних через UPDATE

Далі потрібно було змінити відділ співробітниці Tobi Barnett на `'Sales'`. Головне тут — не забути умову `WHERE`, інакше запит перепише поле всім рядкам одразу:

```sql
UPDATE employees SET department = 'Sales' WHERE first_name = 'Tobi' AND last_name = 'Barnett';
```

![image-1](image-1.png)

### Крок 3. DDL — зміна структури таблиці

Наступне завдання показує, що DDL-команди дають ще більше можливостей, ніж просто читання чи редагування рядків, — можна змінювати саму структуру таблиці. Додав новий стовпець `phone` типу `varchar(20)`:

```sql
ALTER TABLE employees ADD phone varchar(20);
```

![Data Definition Language: успішне виконання ALTER TABLE ADD phone](screenshots/ddl-alter-table-success.png)

Цей крок добре ілюструє, чому DDL-ін'єкція небезпечніша за звичайну DML: зловмисник тут працює не з окремими значеннями, а зі схемою бази в цілому — може додати службові поля для збору даних або видалити критично важливі індекси.

### Крок 4. DCL — видача чужих прав

DCL відповідає за керування доступом, тож тут завдання полягало у видачі повних прав на таблицю `grant_rights` користувачу `unauthorized_user` — фактично змоделював ситуацію, коли атакуючий підвищує собі (чи спільнику) привілеї в базі:

```sql
GRANT ALL ON grant_rights TO unauthorized_user;
```

![Data Control Language: успішне виконання GRANT ALL](screenshots/dcl-grant-success.png)

Три попередні кроки разом добре показують ключову ідею уроку: DML, DDL і DCL-ін'єкції б'ють по різних сторонах тріади CIA — конфіденційність (через SELECT), цілісність (через UPDATE/ALTER) і доступність (через DROP/REVOKE) можуть постраждати незалежно одна від одної.

### Крок 5. Рядкова SQL-ін'єкція — отримання всіх користувачів

Далі урок перейшов від «легальних» практичних завдань до власне ін'єкцій. Бекенд будує запит конкатенацією рядків:

```sql
SELECT * FROM user_data WHERE first_name = 'John' AND last_name = '" + lastName + "'
```

Задача — отримати повний список користувачів, не знаючи жодного конкретного прізвища. Підставив у поле прізвища значення, яке робить умову `WHERE` завжди істинною:

```
Smith' or '1' = '1
```

![Рядкова SQL-ін'єкція: успішне отримання всіх записів з user_data](screenshots/string-injection-success.png)

Після виконання запит фактично перетворився на `... WHERE (first_name = 'John' and last_name = 'Smith') or (TRUE)`, і оскільки права частина умови завжди істинна, база повернула геть усі рядки, ігноруючи фільтр за іменем.

### Крок 6. Числова SQL-ін'єкція

Тут запит будується вже не з рядків у лапках, а з чисел:

```sql
SELECT * FROM user_data WHERE login_count = " + Login_Count + " AND userid = " + User_ID
```

У формі два поля, `Login_Count` і `User_Id`, і вразливе лише одне з них. Спочатку перевірив `Login_Count`, а після невдачі — здогадався, що проблема саме в `User_Id`, і ввів:

```
User_Id: 1 OR 1=1
```

![Числова SQL-ін'єкція: успішне отримання всіх записів разом із номерами карток](screenshots/numeric-injection-success.png)

На відміну від рядкової ін'єкції, тут не потрібно закривати лапки — значення підставляється в запит напряму як число, тож `OR 1=1` одразу робить умову `WHERE` істинною для кожного рядка таблиці. У відповіді, крім іншого, з'явилися номери кредитних карток користувачів — наочний приклад того, наскільки чутливі дані можуть «вилетіти» через таку ін'єкцію.

### Крок 7. Порушення конфіденційності — обхід TAN-перевірки

У цьому завданні я вже виступав у ролі конкретного співробітника — John Smith, TAN `3SL99A`. Застосунок дозволяє переглядати лише власні дані за прізвищем і TAN:

```sql
SELECT * FROM employees WHERE last_name = '" + name + "' AND auth_tan = '" + auth_tan + "'
```

Задача — побачити зарплати всіх колег, не знаючи їхніх TAN-кодів. Оскільки умова побудована через `AND`, досить було «перебити» логіку оператором `OR`, щоб права частина стала завжди істинною і TAN узагалі перестав відігравати роль.

![image-6](image-6.png)

### Крок 8. Порушення цілісності — ланцюжок запитів (query chaining)

Наступний крок — показати, що ін'єкція може не просто читати дані, а й змінювати їх. Ланцюжок запитів працює через метасимвол `;`, який завершує один SQL-оператор і дозволяє одразу почати наступний. Дізнавшись, що колеги Tobi і Bob заробляють більше, вирішив «виправити» це для себе — John Smith, TAN `3SL99A`:

```sql
Smith'; UPDATE employees SET salary = '999999' WHERE last_name = 'Smith' --
```

![Компрометація цілісності через query chaining: зарплата John Smith змінена на 999999](screenshots/integrity-query-chaining-success.png)

Введений рядок фактично розбив один запит на три частини: (1) оригінальний `SELECT`, який знаходить мене за прізвищем; (2) власний `UPDATE`, який одразу після крапки з комою змінює зарплату; (3) `--`, що коментує залишок оригінального запиту й прибирає зайву незакриту лапку. У підсумку моя зарплата в таблиці справді стала найвищою серед усіх співробітників.

### Крок 9. Порушення доступності — видалення таблиці логів

Останній крок демонструє третю складову тріади CIA — доступність. У компанії є таблиця `access_log`, куди пишуться всі мої дії (включно з попереднім кроком!). Щоб замести сліди, застосував ту саму техніку ланцюжка запитів, але цього разу для DDL-команди `DROP TABLE`:

```sql
Smith'; DROP TABLE access_log --
```

![Компрометація доступності: успішне видалення таблиці access_log](screenshots/availability-drop-table-success.png)

Тут спрацював той самий принцип, що й у попередньому кроці, тільки замість `UPDATE` після крапки з комою виконався `DROP TABLE`, який повністю знищив таблицю логів. Після цього в системі просто не залишилось джерела, за яким можна відновити, хто і коли змінював зарплату — доступність цих даних втрачена остаточно.

## Загальні висновки з практики

Пройшовши всі кроки уроку, можу виділити кілька ключових речей:

- **Рядкова і числова ін'єкції відрізняються синтаксисом, а не суттю.** У рядковій потрібно правильно «закрити» лапку, у числовій — нічого закривати не треба, туди можна одразу підставляти вираз (`1 OR 1=1`), оскільки значення й так вставляється в запит без лапок.
- **Query chaining — це вже не «обхід» умови, а виконання зовсім іншого запиту.** Саме тому цей прийом дозволяє не лише читати дані (як у попередніх кроках), а й довільно змінювати (`UPDATE`) чи знищувати (`DROP`) структуру бази.
- **Кожен клас команд SQL б'є по своїй частині тріади CIA**, але межі умовні: DML найчастіше асоціюється з конфіденційністю (SELECT) і цілісністю (UPDATE/DELETE), DDL — з цілісністю і доступністю (ALTER/DROP), DCL — з конфіденційністю і доступністю (GRANT/REVOKE). На практиці ж один і той самий ланцюжок запитів здатен зачепити відразу кілька цих аспектів.
- **Головна причина всіх дев'яти вправ одна й та сама** — застосунок довіряє введеним користувачем даним і просто «зшиває» їх у текст SQL-запиту. Жодного окремого «бага» тут немає, є системна відсутність параметризованих запитів (prepared statements) і перевірки вводу.

## Як мало б бути зроблено правильно

- **Параметризовані запити (prepared statements) / ORM** замість конкатенації рядків — головний і найнадійніший захист, оскільки в такому разі введені користувачем дані ніколи не інтерпретуються як частина SQL-коду.
- **Валідація та санітизація вводу** — додатковий рівень захисту, особливо корисний там, де параметризацію з якихось причин застосувати складно.
- **Принцип найменших привілеїв для облікового запису застосунку** — навіть якщо ін'єкція все ж станеться, обліковий запис без прав на `DROP` чи `GRANT` не дозволить зловмиснику знищити таблиці чи роздати собі привілеї.
- **Ешелонована оборона** — WAF, логування підозрілих запитів, регулярний аудит коду на предмет «сирої» конкатенації SQL — усе це не замінює параметризацію, але суттєво ускладнює експлуатацію, якщо вразливість усе-таки лишилась.

## Висновок

У цій лабораторній я послідовно пройшов шлях від базового ознайомлення з DML/DDL/DCL-командами до реальної експлуатації SQL-ін'єкції: спочатку прочитав і змінив дані звичайними запитами, потім — тими самими діями, але вже через впорскування коду в поле форми, без жодних легітимних прав на ці операції. Найбільш показовими виявились два останні кроки з query chaining: один і той самий прийом (`;` + новий запит + `--`) дозволив спершу підняти собі зарплату (порушення цілісності), а потім замести сліди, видаливши таблицю логів (порушення доступності). Це наочно підтверджує головний висновок уроку — без параметризованих запитів і перевірки вводу навіть проста форма пошуку може стати точкою входу для повної компрометації бази даних.
